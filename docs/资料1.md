## 结论先说

你这个判断基本成立：如果限定在“纯 JS / TS 生态、跟 RDF/SPARQL Web 数据源、RDF/JS、浏览器和去中心化查询生态贴得最紧、标准覆盖最完整”的方向，Comunica 仍然是 JS 世界里最完整的，没有太多同等级对手。它覆盖面很宽：SPARQL Query/Update、RDF/JS source、远程源、本地文件、SPARQL endpoint、各种 RDF parser/serializer、query result serializer、federation、property path、aggregation、RDF-star/triple term 相关函数等。代价就是依赖非常多，工程体积和概念面都大。

但 Oxigraph 是另一个很值得认真看的候选。它不是“JS 生态原生的大而全框架”，而是 Rust 写的 RDF/SPARQL engine，通过 WebAssembly 暴露 JS package。它的优势非常清楚：依赖极轻、API 简单、内存 store 可嵌入、性能潜力好、SPARQL 1.1 Query/Update 能力扎实，并且实际能吃我们现在生成的 RDF 1.2 / RDF-star 风格 Turtle，包括 `rdf:reifies` 指向 triple term 的查询。

我本地实际验证了 `oxigraph@0.5.8`：

- npm 包版本：`0.5.8`
- npm description：JavaScript bindings of Oxigraph
- dependencies：0
- 解包体积：约 8.3 MB
- file count：10
- 最近 npm 修改时间：2026-04-28

它可以加载我们当前 `samples/structural-payload.adoc` 生成的 RDF12 Turtle，并成功运行：

- payload 查询
- heading count 查询
- property path：`aat:containsDirectly*`
- `rdf:reifies ?relation` 查询 triple term

这点非常关键。因为我们不是只要普通 RDF 1.1 triples，我们已经在 RDF12 projection 中使用 RDF 1.2 / RDF-star 风格的 triple term reifier。Oxigraph 能直接跑这个，说明它不是只能处理保守 RDF 1.1 数据。

## Oxigraph 是什么

Oxigraph 是 Rust 写的 SPARQL graph database / RDF store。官方项目定位是实现 SPARQL 标准，支持 SPARQL Query、SPARQL Update、SPARQL Federated Query，也有 standalone CLI/server。JS 包 `oxigraph` 是它的 WebAssembly 绑定。

npm readme 对 JS binding 的定位比较克制：它说 JavaScript API 是 work in progress，目前提供 simple in-memory store，支持 SPARQL 1.1 Query 和 SPARQL 1.1 Update。Store 可以加载 Turtle、TriG、N-Triples、N-Quads、RDF/XML 等格式。当前 readme 还列出 JSON-LD、N3 等 load 格式。JS binding 需要 Node.js 18+，浏览器侧要求现代浏览器支持 WebAssembly reference types 和 JavaScript `WeakRef`。

也就是说，Oxigraph JS 不是一个“只提供 parser 的小包”。它是真正可以执行 SPARQL 的 store，只是 JS binding 当前主要暴露内存 store，而不是完整数据库服务器功能。对我们来说，这个反而合适：我们的书稿投影通常是本地、临时、只读、单文件或少量文件查询，不一定需要长期持久化三元组数据库。

## API 形态

Node 侧用法很直接：

```js
const oxigraph = require('oxigraph')
const store = new oxigraph.Store()

store.load(ttlBuffer, { format: 'ttl' })

for (const binding of store.query(`
  PREFIX aat: <https://micheng.dev/ns/asciidoc-abundant-tree#>
  SELECT ?id WHERE { ?p aat:payloadId ?id . }
`)) {
  console.log(binding.get('id').value)
}
```

`Store.prototype.query(query, options)` 执行 SPARQL 1.1 Query。SELECT 返回 `Map` 数组，key 是变量名，value 是 RDF term。CONSTRUCT / DESCRIBE 返回 Quad 数组。ASK 返回 boolean。

`Store.prototype.load(data, options)` 可以加载序列化 RDF。`data` 可以是 string、UInt8Array 或 iterable。`format` 是必须项，例如 `ttl` / `text/turtle`。这对我们非常舒服，因为 `asciidoc-abundant-tree` 当前可以直接输出 Turtle 字符串或文件；后续甚至可以不落盘，直接把 serializer output 传给 Oxigraph。

## 我对我们数据做了什么验证

我先用当前发布后的 CLI 生成 sample 的 RDF12：

```bash
node dist/cli.mjs samples/structural-payload.adoc --format rdf12 > tmp/structural-payload.ttl
```

然后临时安装 `oxigraph@0.5.8`，用 Node 加载 TTL：

```js
const fs = require('node:fs')
const oxigraph = require('oxigraph')
const ttl = fs.readFileSync('tmp/structural-payload.ttl')
const store = new oxigraph.Store()
store.load(ttl, { format: 'ttl' })
console.log('size', store.size)
```

结果：

```text
size 112
```

然后跑 payload 查询：

```sparql
PREFIX aat: <https://micheng.dev/ns/asciidoc-abundant-tree#>
SELECT ?kind ?id WHERE {
  ?p aat:payloadKind ?kind ;
     aat:payloadId ?id .
}
ORDER BY ?id
```

结果：

```text
payload node delivery-policy-payload
payload edge rel-delivery-capacity
```

跑 heading count：

```sparql
PREFIX aat: <https://micheng.dev/ns/asciidoc-abundant-tree#>
SELECT (COUNT(?h) AS ?count) WHERE {
  ?h a aat:Heading .
}
```

结果：

```text
headings 4
```

跑 property path：

```sparql
PREFIX aat: <https://micheng.dev/ns/asciidoc-abundant-tree#>
SELECT ?headline WHERE {
  ?root aat:headline "root" ;
        aat:containsDirectly* ?node .
  ?node aat:headline ?headline .
}
ORDER BY ?headline
```

结果包含：

```text
root
我是3级标题
运力规则
配送策略
```

最后跑关键的 triple term / reifier 查询：

```sparql
PREFIX aat: <https://micheng.dev/ns/asciidoc-abundant-tree#>
PREFIX rdf: <http://www.w3.org/1999/02/22-rdf-syntax-ns#>
SELECT ?edge ?relation WHERE {
  ?edge a aat:XrefEdge ;
        rdf:reifies ?relation .
}
```

Oxigraph 成功返回 edge IRI 和 relation triple term，形态类似：

```text
reifies urn:aat:doc:...#xref-edge-l8-c8-o0
<...#heading-l5-o0> <https://micheng.dev/ns/asciidoc-relation#depends-on> <...#heading-l41-o0>
```

这说明 Oxigraph 对我们当前 RDF12 输出的核心形态是可用的，不只是“理论上支持 RDF-star”。

## 和 Comunica 的本质差异

Comunica 是查询框架，Oxigraph 是嵌入式 store/engine。

Comunica 的强项是 source 多样性。它可以把本地文件、远程 RDF、SPARQL endpoint、RDF/JS source、hypermedia source 等组合起来查询。它适合“在 Web of Data 上查询”，也适合在 JS 应用里接 RDF/JS 流和数据源。它的架构是 actor/bus/mediator，非常模块化，覆盖面大，但依赖树巨大。

Oxigraph 的强项是内存 store 简洁。你把 RDF load 进去，然后 query。它不像 Comunica 那样把整个 Web 数据访问生态都带进来；它更像 SQLite 之于 SQL：本地、嵌入、可预测、轻依赖。它的 JS 包没有 npm dependencies，但有 WASM 二进制体积。

对我们的项目，这个差异非常重要。

如果目标是“作者本地查一个生成出来的 TTL”或“CLI 内部生成 RDF 后立即查询”，Oxigraph 很合适。它不需要 Java，也不需要下载 500 个 npm 包。它可以作为一个轻得多的嵌入查询内核。

如果目标是“查多个远程 RDF source、SPARQL endpoint、RDF/JS source、前端数据流、联邦查询”，Comunica 更合适。

## 标准支持判断

Oxigraph 官方明确支持 SPARQL 1.1 Query 和 SPARQL 1.1 Update。项目 wiki 提到它对 SPARQL 1.1 Query 有稳定支持，但也列出一些和规范的差异，例如 federated query 中 variable service URL 等场景有限制；它还说明会按 RDF 1.1 处理一些和 SPARQL 1.1 不完全一致的字面量语义，比如 plain literal datatype、数值/boolean/calendar/duration literal normalization 等。

RDF-star 方面，npm readme 写到 RDF-star 已实现，Quad 可以作为 subject 和 object。W3C RDF-star implementations 页面也列出 Oxigraph 有 Rio Turtle 和 SPARQL 的 implementation reports。项目 wiki 还提到 SPARQL-star Update 实现跟随 Community Group Report Draft，属于 experimental，未来可能随着 W3C RDF-star 工作组变化而改变。

这意味着：

- 对 SPARQL 1.1 主体能力，Oxigraph 可以认真依赖。
- 对 RDF-star / RDF 1.2 相关能力，Oxigraph 确实在跟进，不是完全没有。
- 但对“最新标准完全覆盖”，需要比 Comunica/Jena 更谨慎地用测试锁住。

尤其我们现在用的是 `rdf:reifies` + triple term。Oxigraph 实测可查询。但如果后续要用 SPARQL 1.2 新函数、RDF 1.2 新语法边缘、复杂 triple term 构造、SPARQL-star update，就不能只看一次 sample 测试，需要做兼容矩阵。

## 依赖和体积

这是 Oxigraph 很大的优点。

Comunica file package 第一次 `pnpm dlx` 时解析/下载了五百多个包。它不是坏事，那是能力覆盖的成本。但如果我们把它作为 `asciidoc-abundant-tree` 的主 dependency，会显著改变安装体感和包维护面。

Oxigraph npm 包是 0 dependencies。解包体积大约 8.3 MB，因为有 WASM/Rust 产物，但依赖图非常干净。对 Node 项目来说，这种“一个重一点的 native/WASM 包”往往比“几百个 JS 包”更可控。

如果未来我们要给 CLI 增加：

```bash
asciidoc-abundant-tree query sample.adoc --sparql 'SELECT ...'
```

Oxigraph 会让安装和发布更可控。用户不需要 Java，不需要 Jena，也不需要 Comunica 的大量依赖。

## 风险

第一，JS binding 官方仍说 work in progress。这不是不能用，但说明 API 稳定性要谨慎。相比 Comunica 的 JS API，Oxigraph JS binding 可能更像 Rust 项目的附属入口。

第二，WASM 环境限制。Node 18+ 没问题，我们项目 Node 24 没问题。浏览器端则要求 WebAssembly reference types 和 WeakRef。现代浏览器大多可以，但如果要做广泛兼容的网页工具，要实测。

第三，生态集成不如 RDF/JS 原生。Comunica 和 RDF/JS source/dataset/stream 的生态连接更自然。Oxigraph 有自己的 term/quad/store API，虽然看起来接近 RDF/JS datamodel，但它不是完整围绕 RDF/JS source pipeline 设计的查询框架。我们如果内部已经有 N3 Store 或 RDF/JS DatasetCore，要么 serialize 成 Turtle 再 load，要么写转换层。

第四，远程/federation不是它在 JS 包里的核心使用方式。Oxigraph 本体支持 SPARQL Federated Query，但 JS binding 的直接读写体验主要是 Store load/query/update。若我们要把“查远程 RDF + 查本地 TTL + 查 endpoint”作为核心，Comunica 更适合。

第五，性能需要用我们的数据测。Rust 内核给人直觉上会快，但 WASM、load、serialization、JS bridge 都会影响实际表现。我们要测三类数据：单本书 TTL、多本书 TTL、超大聚合 TTL。查询要覆盖 heading count、xref edge、property path、GROUP BY、unbound audit、triple term。
